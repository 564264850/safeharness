# SafeHarness 上线准备评审

评审日期：2026-11-11。依据当前源码、M4 开发集验收与本次临时故障注入。本文是工程评审和建议路径，不代表新增功能已实现、已完成生产验证或获得外部认证。

当前定位：具备自主核心协议的 Agent 安全运行时与执行控制平面原型。M0–M4 完成了原型路线的交付条件；承接真实客户、外部副作用和长期运行的上线门槛尚未满足。原计划的 M5 反思/上下文优化应后移，优先建立可恢复运行、企业评测与预生产运维能力。

| 维度 | 当前证据 | 评审判断 |
| --- | --- | --- |
| 安全执行 | Gateway、严格参数、范围授权、审批、Docker 隔离 | 有实质实现，仍限固定环境和单一信任域 |
| 可靠性 | SQLite/PG 意图、原子业务回执、幂等恢复、并发验证 | 工单写恢复成立，普通 Agent/Coding 任务恢复不完整 |
| 评测 | 120 合成脚本实例、少量真实 Provider、OpenJudge、A.I.G | 足够支持开发回归，不足以证明生产可靠性和模型泛化 |
| 服务能力 | 本机 FastAPI、静态角色、两进程 PG 测试 | 服务原型，未形成持久调度、租户隔离和运营闭环 |
| 上线运维 | 锁文件、固定镜像、CI 配置、迁移及打包验证 | 缺容量/稳定性、监控告警、备份恢复、灰度回滚等实测 |

自主实现的价值主要位于 Runtime、Gateway、审批摘要绑定、执行意图/回执协议、数据库并发、控制面验证及证据关联。FastAPI、PostgreSQL、Docker、DeepSeek、OpenJudge、A.I.G 为外部能力。已有自主工程核心，尚无实验支持将其称为新的算法或独创分布式理论。求职展示应围绕可解释的设计取舍、故障复现和可测量的机制收益。

## 已确认的问题与当前缺口

1. **普通异常收敛已在 R1 修复。** 原先已复现的执行器/验证器异常悬挂现由统一失败合同处理：确定失败保存 FAILED，执行结果不明保存 NEEDS_REVIEW，状态与安全错误记录同事务提交；存储无法写入时明确报错。并发终态和原工单回执恢复保留。见 [R1 记录](runtime-correctness.md)。本项修复不包含进程强杀后的通用恢复、失联扫描器或完整人工处置台，其他上线阻断项继续成立。
2. **运行与 HTTP 进程耦合（上线阻断）。** `/run` 同步执行；进程内信号量为 2。缺持久任务队列、worker 租约、心跳、执行代次隔离和崩溃接管。当前 `/resume` 恢复的是审批工单操作，不能泛称所有 Agent 任务可断点续跑。Coding 快照与模型上下文只在内存中的部分尚需持久化。
3. **幂等边界尚未覆盖提交和真实外部适配器（上线阻断）。** 同一个审批/操作 ID 有防重能力，重复 POST 创建新任务没有客户端请求幂等键。业务实现仅为受控 mock，拥有原子回执，不能推导到所有 HTTP API。需区分可查询幂等回执、可查资源状态、可补偿以及无法确认四类工具能力。
4. **控制事务跨越业务调用（扩展前必须重审）。** `TaskStore.resume` 在持有任务行锁期间查询/执行业务适配器。当前本地 mock 可验证正确性，远端慢调用会延长锁持有并影响取消与连接容量。后续需要短事务领取、租约/执行代次、稳定幂等键和回执协议；不能简单把调用移出锁外而破坏现有取消/派发一致性。
5. **授权和审批尚处单信任域。** 身份与角色来自启动时的本地配置；无 tenant_id、正式身份提供方、token 生命周期、即时撤权和租户额度。审批绑定参数，但没有资源 expected_revision 等前置条件；对状态敏感工具需要定义并发编辑后批准是否仍有效。单租户受控部署可以明确缩小范围，多租户承诺则必须补齐整条数据与执行隔离链。
6. **恢复和使用结果未形成完整产品接口。** NEEDS_REVIEW 无人工核对/处置工作台；HTTP Coding 执行没有像 CLI demo 一样持久化并提供完整 patch/独立验证报告。需要统一 TaskSpec、环境/工具适配器、Artifact 和 verifier 合同，减少固定 scenario 与 fixture 的耦合。
7. **Trace 不能代替运维可观测性。** 尚无任务积压、租约失效、重复派发、业务回执未知、worker 清理失败、Provider 错误和费用异常的指标/告警。健康接口未检查依赖就绪，Trace 无分页/保留策略，数据库和本地预算也未建立长期容量与恢复验证。
8. **评测覆盖仍是开发覆盖。** 30 Coding 为 10 函数 × 3 bug，30 IT 为 10 工作流 × 3 初始状态，40 攻击为 5 类边界，20 故障中 10 个可恢复、10 个安全停止。固定场景重复不等于独立风险覆盖。A.I.G 成功验证的是合成负对照及加固重放，不能宣称发现或证明消除了生产漏洞。

## 建议的上线验收体系

| 层次 | 应补的测试 | 应交付的证据 |
| --- | --- | --- |
| 协议不变量 | 状态机属性测试、状态并发交错、审批篡改/过期/撤权、提交/派发/回执防重 | 每个接受的逻辑操作对应唯一记录；失联操作不得无证据重复执行 |
| 应用安全 | 适用的 OWASP ASVS 5.0.0 条目、身份/租户/授权/密钥/审计 | requirement ID → 测试 → 结果 → 证据；不适用项给出边界，不称认证 |
| Agent 效果与攻击 | 按场景族分离开发/保留集、受限外部基准、真实模型多次运行 | 正常效用、攻击尝试/实际影响/未知、误拒绝、延迟及费用；脚本与真实模型分开 |
| 机制收益 | 同模型/工具/预算/任务条件下，对安全和恢复机制做隔离对照 | 明确开启机制解决了什么失败，代价是多少；危险对照仅在合成隔离环境运行 |
| 系统负载 | 混合长短任务、突发、队列积压、多租户公平性、24 小时起步的稳定性 | 接受/拒绝/完成/待核对总数守恒，队列时延与执行时延分开，资源和连接不持续泄漏 |
| 故障与发布 | kill API/worker、业务提交后丢响应、数据库短时不可用、Provider 429/5xx、取消竞争、备份恢复、滚动更新/回滚 | 可恢复窗口达到预定时限，不可确认项形成可处置记录，已接受任务不静默丢失 |

负载和故障测试可主要使用可控假 Provider 与独立 HTTP mock 业务服务，免费覆盖协议与调度；真实模型只用预算明确的小批量验证语义。假 Provider 的吞吐不能用于宣称真实模型吞吐。0/40 攻击与 10/10 恢复的 95% 区间仍分别约为 [0, 8.76%]、[72.25%, 100%]，不足以证明大范围安全性或生产恢复 SLO。

## 可行的预生产路径

1. 修复已复现的异常收敛，建立通用任务/调用/执行尝试/产物模型，明确幂等、取消和未知结果协议。
2. API 只负责持久化接受任务；独立 worker 领取执行。优先以 PostgreSQL 的持久调度实现小规模部署，再根据压测选择额外组件。
3. 建立受控试运行环境：两 API 副本、独立 PG、2–4 个受限 worker、独立 HTTP mock 业务、统一指标与日志。先同机多进程，需模拟机器/网络故障时再拆两台 Linux VM。
4. 在明确资源档位上，从 10–20 个并发已接受任务、长短任务混合和 24 小时稳定性测试起步。这些是拟议档位，尚未实测；API SLO、恢复时限、容量和预算应在基线测量后固定。
5. 演练审批等待中的升级、在途写入时进程退出、备份恢复后的防重和版本回滚。先使用合成流量；如未来有真实流量，只能在不提交真实写入的影子模式下开始验证。
6. 产出发布候选的不可变版本、测试矩阵、容量报告、故障演练记录、回滚记录和发布评审结论，再开展小范围试运行。

不要求个人项目先拥有大型集群；要求它在声明的用户数、资源、并发与风险边界内，具备可重复的验证和运营证据。建议重点深化“可验证的副作用恢复协议”和“安全与正常效用的受控评测”两个自主核心，先建立上线条件，再做原 M5 的反思优化。
