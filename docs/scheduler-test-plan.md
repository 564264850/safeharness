# 持久调度与自动恢复：实施及测试计划

规划日期：2026-11-13。本文件描述待实施方案和验收条件，不表示持久调度器或本轮新增测试已经完成。当前已有检查点、generation/owner 校验、显式恢复、审批续跑和业务回执恢复，可作为基础复用。

实施更新：[S1 持久接单](scheduler-s1.md)、[S2 独立 worker](scheduler-s2.md)、[S3 租约心跳](scheduler-s3.md)、[S4 自动恢复](scheduler-s4.md) 已完成；[S5–S7 实施与验收](scheduler-s5-s7.md) 补齐脚本工单的调度闭环。下文全模块门槛与故障矩阵仍是完整目标，实际通过范围和运行时长以该文及机器证据为准。Coding 调度的孤儿容器接管 F19 和 24 小时运维验收不在本轮已完成范围内。

## 用普通语言理解目标

- API 是接单窗口，成功接收的任务必须已经写入数据库。
- 队列是数据库中的待办清单，不依赖某个 Python 进程的内存。
- worker 是执行任务的独立进程，调用已有 Harness。
- 租约是有期限的执行资格，心跳用于续期。
- 扫描器定期检查失联任务，按恢复规则重新安排或停止等待人工核对。
- generation 是执行资格的代次，新执行者接管后，旧执行者不能继续提交结果或启动新工具。

API 重启后，待办清单应仍存在；worker 退出后，任务应被发现并妥善处置。自动恢复不要求所有任务都成功，有些不确定副作用必须进入 NEEDS_REVIEW。

## 范围和环境

首版复用 PostgreSQL 保存任务队列，通过短事务领取任务，不额外引入 Redis/Celery/Kubernetes。实现时可采用 FOR UPDATE SKIP LOCKED 处理多 worker 竞争，领取与所有权更新必须原子提交，不能在事务里执行长时间模型/工具调用。

本机使用一个专用测试 API、两个独立 worker、独立的扫描进程或可独立运行的扫描命令、专用 PostgreSQL 测试数据和现有 Docker worker。数据库和容器使用专用标签及命名空间，故障脚本只能操作本次演示登记的 PID/容器，不应停止其他项目或删除真实数据。

第一轮全部使用确定性的脚本 Provider，不读取 API 密钥，不调用付费模型。独立 HTTP mock 业务服务随后加入，用来测试控制面无法原子提交的外部副作用。只在数据库内 mock 不能证明远程接口的恢复正确性。

调度状态与现有任务业务状态分别定义：待领取/已领取/延后重试属于调度元数据；审批等待、成功、失败、取消和待人工核对沿用任务协议。租约、检查点 owner/generation 和任务 revision 必须统一判权或明确绑定，避免两套所有权互相矛盾。

迁移测试还须证明原有任务、审批和调用记录被保留，旧任务不会因为升级而突然被自动执行。首版仅对明确支持的新任务启用自动调度。

## 分步实施和测试

| 阶段 | 先实现什么 | 自动测试与通过条件 | 亲手观察 |
| --- | --- | --- | --- |
| S1 持久接单 | 队列表、迁移、提交与入队同事务，复用请求幂等键 | 提交前/后崩溃、重复提交、旧库迁移；收到成功响应的任务都有持久记录且最多一个逻辑队列项 | 不启动 worker，提交任务，重启 API，原 ID 仍待执行 |
| S2 独立领取 | worker 命令、原子领取、短事务、调用现有 Harness | 两个独立进程同时竞争；一个任务在同一代只有一个领取者；多任务不被永久饿死 | 启动两个 worker，看到任务被分配且无双重执行 |
| S3 租约与续期 | DB 时间、独立心跳、所有权代次 | 未到期不能接管；长工具调用超过租约时仍正确续期；暂停 worker 后过期；迟到心跳无法续旧代 | 长任务执行时观察心跳，任务不被误判失联 |
| S4 失联扫描与恢复 | 有界扫描、恢复分类、接管与取消复核 | 多扫描器竞争、重复扫描、故障窗口、过期/取消；安全任务自动恢复，未知副作用进入 NEEDS_REVIEW | 在指定检查点强杀 worker，另一个 worker 接管 |
| S5 旧执行者隔离 | 所有权检查覆盖状态、检查点、工具派发和结果记账 | 冻结旧进程、接管后再释放；旧代写入与新工具派发被拒；外部在途请求按幂等回执核对 | 看到旧 worker 的明确拒绝事件，业务写入未增加 |
| S6 审批与副作用 | 批准后持久唤醒、等待时释放执行资格、外部回执核对 | 无批准不执行；批准重复通知只安排一次逻辑续跑；拒绝/取消不复活；业务提交后丢响应不盲目重发 | 人工批准后自动继续，无需手动调用 resume |
| S7 模块集成验收 | 自动故障脚本、报告、连续运行 | 混合任务、API/worker/DB 故障、预算与重试上限、容器清理；任务数可核对，无无主任务或无限重试 | 看一份完整报告和每个故障的时间线 |

每阶段先通过有针对性的测试，再进入下一阶段。所有权、状态与副作用语义发生变化后，重跑已有相关回归；最后运行完整回归和固定开发验收集。

## 核心故障矩阵

| 编号 | 注入点或操作 | 合格结果 |
| --- | --- | --- |
| F01 | 提交事务前退出 API | 不返回成功；没有半条任务/队列记录；同幂等键可重试 |
| F02 | 提交已持久化但 HTTP 响应丢失 | 同幂等键重试返回同一任务，不创建第二次逻辑任务 |
| F03 | 入队后、领取前重启 API | worker 可照常领取，任务不依赖 API 内存 |
| F04 | 两 worker 同时领取同一任务 | 同一代只有一个所有者；另一方不执行该任务 |
| F05 | 领取提交后、初始检查点前强杀 | 扫描器能识别并按明确的初始化恢复规则处理，不永久卡住 |
| F06 | 安全检查点处强杀 worker | 租约到期后接管，恢复已保存的上下文、工具队列及文件快照；新调用有新的 attempt |
| F07 | 工具或模型调用时间超过租约 | 正常心跳继续，不被错误地重复派发 |
| F08 | 旧 worker 冻结，到期接管后再恢复 | 旧心跳/结果/检查点/新派发被拒绝；只有新代能推进任务 |
| F09 | 工具请求已发出，但执行结果未知 | 不能仅因租约过期就重做；可查询则先核对，无法确认则 NEEDS_REVIEW |
| F10 | 业务已提交，但控制面尚未记回执就退出 | 查询稳定幂等键的原回执；已确认写入次数为 1，随后继续循环 |
| F11 | 回执存在，但下一检查点或队列完成标志未提交 | 核对已持久化结果，不重做副作用、不覆盖终态 |
| F12 | 等审批时重启所有执行进程 | 保持 WAITING_APPROVAL，不自动批准、不循环占用 worker |
| F13 | 批准后、唤醒前退出；或重复唤醒 | 批准与唤醒具有原子记录或可补偿扫描，无漏续跑；只出现一次有效执行 |
| F14 | 取消/拒绝与扫描领取同时发生 | 取消/拒绝不会被恢复成活跃任务；在途已发生写入如实核对 |
| F15 | PostgreSQL 短时不可用、心跳提交失败 | worker 停止获得新的派发权；已有在途操作核对结果；恢复后旧代不能抢回所有权 |
| F16 | 检查点损坏、配置或镜像不兼容 | 拒绝不安全恢复并记录原因，扫描器不会无限尝试相同失败 |
| F17 | 重复扫描、重启扫描器、两个扫描器并行 | 扫描本身幂等，同任务不会产生多个有效恢复者 |
| F18 | 恢复次数用尽、任务总预算/期限用尽 | 按明确规则结束或人工核对，不因重启重置计数与预算 |
| F19 | Docker 容器运行中控制 worker 强杀 | 按所有权标签发现并回收旧容器，防止孤儿进程持续运行或争用工作区 |
| F20 | 已终态任务重复投递 | 不重新执行，记录或忽略重复调度，保持原结果 |

租约与 generation 只能阻止控制面接受旧执行者结果，不能撤销已经发往外部服务的请求。F08/F09/F10 必须结合工具能力、稳定幂等键和业务回执检查，不能据此声称任意工具 exactly-once。

## 测试方法

**规则测试：** 使用可控制的时钟和数据库时间接口测到期边界、退避与预算，不依赖大量 sleep。测试正常心跳、刚到期、迟到心跳、取消竞争等。

**真实 PostgreSQL 并发测试：** 使用两个独立进程/连接及同步屏障，同时领取或恢复同一任务。不能仅用 SQLite 或线程模拟替代数据库竞争结论。

**进程故障测试：** 使用命名注入点和进程间事件，确认到达目标窗口再强杀/冻结，避免“随便等几秒后 kill”导致根本没有测到目标窗口。旧 worker 在测试控制事件上阻塞，接管后释放；实际在途外部 HTTP 请求另行覆盖。

**端到端测试：** 通过真实 HTTP 提交任务，分别重启 API、worker、扫描器和隔离的数据库；从任务状态、调用账本、业务回执和容器列表验证结果。内部状态只能作为证据之一，不能用日志中的“恢复成功”代替实际业务结果。

## 初始门槛（待测目标）

- 测试配置建议心跳 2 秒、租约 10 秒、扫描间隔 1 秒；这些是加速演示用参数，不直接作为生产默认值。
- 在 PostgreSQL 和备用 worker 健康、有空闲执行槽的本机条件下，安全任务从最后一次成功心跳到重新领取，先以 15 秒为观测目标。完成时间单列；不把模型执行耗时算作接管耗时。正式门槛在基线测试后固定。
- 关键竞争/崩溃窗口至少重复 30 次并保留失败；有限样本通过不能证明所有并发交错都正确。
- 每个成功接收的逻辑任务，在任一检查时点均可归入互不重叠的排队、执行、审批等待、人工核对或终态类别；数量合计等于去重后的接收数。
- 无静默丢失、无未被发现的长期无主任务、无越过审批/取消的派发；在支持幂等回执的测试业务中重复副作用为 0。
- 先以 1/2/4 个执行槽进行基线，完成 1 小时混合任务运行；24 小时稳定性与备份恢复属于后续完整模拟运维验收，不能用短测替代。

## 用户亲手参加的第一次演示

准备一个可查询的任务，先不启动 worker。用 API 提交后得到 task_id，查询发现它在等待执行。关闭 API，再启动 API，查询同一个 ID，任务仍存在。然后启动 worker，观察它领取并完成任务，检查结果与业务状态。

第二次演示增加“执行中退出和自动接管”。命令与预期输出见 S4、S5–S7 指南，故障注入只针对本次演示登记的进程。当前已提供 `worker` 和 `recover-queue --watch`，自动恢复范围受场景白名单约束。

## 每阶段的交付

保存版本/配置指纹、任务 ID、worker ID、generation、故障注入点、心跳与领取时间、调用/尝试身份、业务实际写入次数、容器回收结果，以及逐项测试报告。每阶段汇报“增加了什么、解决哪个故障、如何验证、还缺什么”，并提供一组可手工复现的命令。
