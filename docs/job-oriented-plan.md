# SafeHarness 求职优化计划

制定日期：2026-11-14。目标：广投 Agent 开发、AI 应用工程，并兼顾 Agent Runtime／平台基础设施方向。按依赖与验收推进，不按固定周数推进。本文件是待实施计划，不代表所列功能已经交付。

## 定位与当前基线

项目定位为“具备可信工具执行和持久恢复能力的 Agent 运行框架，并提供可运行的应用实例”。现有 Runtime、Context、Checkpoint、Gateway、审批、沙箱与调度协议继续复用。

S5–S7 历史基线包含 483 项回归、120 个固定开发验收实例、四个窗口各 30 轮共 240 个重复测试实例，以及一小时脚本工单运行：1,165 个任务到达预期终态，291 次批准写入无重复。2026-11-15 的求职阶段复验新增暂存区安全与审批撤权覆盖后，本机和 GitHub Actions 均为 493 项回归通过、0 跳过；GitHub Actions 同时通过 120 个固定开发验收实例。这些数字不相加称为独立场景数。真实 DeepSeek 已有显式运行入口；自动调度仍仅覆盖 scripted 工单。历史证据见 [S5–S7](scheduler-s5-s7.md) 和 [验收索引](evidence/scheduler-s5-s7.json)，本轮发布及 CI 记录见[公开基线摘要](evidence/baseline/README.md)。

求职优化优先覆盖：真实模型执行、工具集成、上下文与恢复、人工审核、应用工作流、效果评测，以及可复现交付。完整上线运维作为后续路线保留。

| 5 评测与机制对照 | 真实任务、任务族保留集、重复实验、失败分析 | 能说明完成效果、机制作用及成本代价 |

阶段 1 完成后即可用现有版本开始投递；后续阶段按真实进展更新简历，不等待所有增强和生产化工程结束。

## 阶段 1：交付基线与缺陷分流

1. 归档现有源码、锁文件、测试和必要的公开证据，建立真实版本记录。若现在才开始使用 Git，如实记录现有代码的首次归档，后续使用真实增量提交，不重建虚构历史。
2. 检查忽略规则和打包内容：凭据、环境文件、数据库、虚拟环境、原始私有轨迹不进入仓库；保留报告索引和少量可公开复现结果。已有 `artifacts/` 忽略规则继续保留，不为缩小仓库删除历史证据。
3. README 首屏依次展示：用途、架构图、可运行示例、启动步骤、关键证据与支持范围。详细阶段记录移到后面的文档索引。
4. 在干净环境执行现有 CI，分别报告单元测试和启用 Docker／PG 的集成测试，归档每轮失败。未实际运行的远端 CI 不贴成功徽章。
5. 将外部评审的问题拆成“已复现缺陷／待验证风险／有意的实验限制／可选改进”。优先复现控制事务内业务 I/O、派发时授权、Provider 超时与错误映射；不能根据静态标签直接宣称存在漏洞。影响核心正确性的已复现问题先修复，再开放新功能。

验收：干净环境可按文档复现现有演示；仓库无私有凭据和大体积运行产物；CI 有真实结果；问题列表附复现、影响与处置。远端地址、仓库可见性和发布范围由用户指定后落实。

## 阶段 2：真实 DeepSeek 持久调度（原 S8）

2026-11-15：阶段 2 在受限 ticket 范围完成。DeepSeek 已接入队列、审批、checkpoint 恢复及共享费用账本；两次真实 API 集成演练通过，审批身份与业务数据为本地合成环境。范围、验收命令和测试结果见[阶段 2 实施记录](phase2-execution.md)。本文开头关于自动调度仅覆盖 scripted 的描述为阶段 1 历史基线。

| 步骤 | 实施 | 验收 |
| --- | --- | --- |
| 2.1 配置与准入 | worker 从可信配置构建 Provider；任务绑定模型、工具、验证器和预算策略；先开放工单 | 请求参数不能选择密钥、任意端点或自行启用付费权限 |
| 2.2 调用及费用持久化 | 关联模型 call／attempt、费用预留、返回产物及用量；所有 worker 共用同一账本位置和预算身份 | 重启不重置预算；未知用量保留预留；密钥不进入检查点或公开 Trace |
| 2.3 请求边界与失权处理 | 审查后台 HTTP 的执行上下文，在派发、重试和接收结果时检查当前资格 | 失权或迟到响应不能触发新的工具调用或覆盖新代结果；在途请求可能计费的情况如实记账 |
| 2.4 有状态恢复 | 恢复上下文、待执行工具、历史结果、累计步数与期限；扩展恢复分类器 | 已确认工具不重复执行；已保存模型结果可复用；配置不兼容时拒绝恢复 |
| 2.5 真实审批闭环 | 模型提出写入，独立操作员审批，worker 恢复后继续读取和验证 | 批准前业务不变；批准后自动继续；拒绝、取消后不复活 |
| 2.6 故障与真实 API 验收 | 可控假 Provider 覆盖协议与崩溃窗口，再运行小批量真实 DeepSeek 任务 | 记录任务、费用、调用、检查点和回执；区分真实结果与模拟结果 |

请求已发出但结果未可靠保存时，默认保留未知记录并停止待核对；不把它视作未调用。未来若允许重算，需要明确策略、独立 attempt 和仍然有效的累计预算。单机多进程可先复用现有持久账本；跨机器运行时再选择共享后端。

亲手演示：API 关闭后 worker 完成读取；人工批准后自动续跑；指定安全检查点退出后由新 worker 恢复。每个演示都检查真实业务结果，不用最终回答文本代替验证。

## 阶段 3：工具／业务扩展与受控 MCP

1. 抽出最小的可信应用注册边界：应用 ID、工具 Schema、执行适配器、策略、资源范围、验证合同和配置版本。保留现有场景作为兼容样例，不重新实现 Runtime。
2. 将所需业务能力通过注册接入。增加第二个受控适配器时，不修改核心循环、检查点所有权和审批状态转换。业务专用规则可以保留在适配器中。
3. 接一个宿主配置的本地 MCP 服务，先支持受控只读工具，覆盖工具发现、参数校验、调用、错误、超时及输出上限。
4. MCP 工具仍经过统一 Gateway、资源授权、调用身份链和审计。服务器位置、启动命令及权限不由模型提供；工具描述和 annotations 不直接授予权限。
5. 首版写操作继续使用已验证的原生工单审批／回执协议。支持 MCP 写工具前，必须明确它的审批绑定、幂等与回执能力；未知副作用停止待核对。

验收：同一控制面可运行原生工具和 MCP 只读工具；未知工具、越界资源、Schema 错误、超时和断开连接都有测试；新增适配器只需实现／注册规定接口，不改 Runtime。MCP 服务为受控测试服务时如实标注，不称为任意第三方服务支持。

## 阶段 4：一个应用实例与最小控制台

主场景采用研发运维助手：接收问题 → 检索故障文档 → 查询多张工单 → 生成带依据的处置计划 → 人工批准 → 修改工单 → 回读验证 → 输出处理报告；中断后从已确认状态继续。

- 业务服务可以自建，数据可以合成，但应支持多张工单与不同授权范围；分别标注真实模型、模拟数据和业务服务来源。
- 检索先覆盖文档内容、来源、片段和引用核对；针对明确要求 RAG 的 JD，再加入 embedding／混合检索等能力，并单独验证检索效果。关键词检索不能写成已经实现向量检索。
- 控制台只做任务提交与列表、执行详情、审批参数与摘要、待核对原因、产物和事件流。前端角色选择不能改变服务器权限，不硬编码服务 token。
- 优先实现任务事件 SSE：事件序号、断线续读、权限过滤和重复事件处理。先展示已提交的任务与工具事件，不把它称为模型逐 token 流式输出。
- NEEDS_REVIEW 首版展示证据与允许的安全操作；人工结论追加审计，不能直接把未知任务改成“验证成功”或盲目重发副作用。

验收：浏览器可完成提交、审批与查看最终报告；事件来自同一个后端；跨用户任务不可见；审批前后状态和实际写入次数可核对；新增失败任务可以定位原因。

## 阶段 5：真实任务评测与机制对照

先写实验协议，再调试提示词。建议从 20–30 个有明确合同的代表性任务起步，具体规模根据试跑成本校准，不以模型数量作为完成条件。

1. 按任务族划分开发集与保留集，避免把同一模板的变体随机分到两边。用于分析和调参的保留任务应转为开发数据，后续补充新的保留任务。
2. 先使用一个真实模型做重复实验，报告每次运行和所有失败，再决定是否加入第二个模型。模型、提示词、工具、版本、预算和重试政策均记录。
3. 分别定义正常任务完成、越权被拒、审批暂停、故障恢复和安全停止。预期拒绝不计作正常任务完成，也不误记为机制失败。
4. 报告合同通过率、违规派发／实际越权结果、重复业务写入、恢复耗时、模型费用与未知用量，以及排队／模型／工具／总时延。时延不混用为生产吞吐结论。
5. 选择一项有用的机制做对照，例如固定预算下的上下文压缩，或相同故障窗口下的自动恢复。实验保留权限边界，危险对照只在合成隔离环境运行；结果不预设必须提升。
6. 开发回归、模拟协议测试、真实模型任务和保留集成绩分别展示。有限样本给出分母和不确定性，不宣称生产认证。

验收：可重跑的实验入口、冻结任务清单、环境指纹、每例结果与失败分类、费用／时延表，以及至少一项机制对照。真实 API 只承担语义验收，可控接口承担多数故障注入。

## 阶段 6：求职材料与本人掌握

- Agent／AI 应用版：突出真实任务、工具与检索集成、上下文、人工审核、应用结果和效果评测。
- Runtime／平台版：突出有界循环、持久状态、租约与 generation、回执防重、故障验证。
- 两版使用同一套事实和证据，不改变功能完成范围。偏 RL／SFT／模型训练的 Agent 算法岗需要额外训练实验经历，本项目不替代该能力证明。
- 整理一页项目介绍、架构图、三分钟演示，以及审批、写入提交后崩溃、旧 worker 失权、验证器误判四个可亲手复现的设计故事。
- 本人能讲清 API、worker、数据库、模型和业务服务各自负责什么，哪些失败可重试、哪些必须停止，以及机制的代价。

验收：招聘方能快速看到项目用途、运行入口、主要设计、真实结果和限制；本人能独立运行演示、定位一个失败并解释修复。

## 暂缓项与持续规则

完整 Coding 自动调度及 F19、24 小时运行、备份恢复、进程托管、多租户、全套 OTel／Prometheus、长期记忆和多 Agent 编排继续留在后续清单。若某项是目标 JD 的明确重点，或已经影响本轮功能正确性，再提前处理。不为求职关键词整体重写现有存储层，也不把第二个真实模型、复杂前端或新中间件作为投递门槛。

每一步保存变更说明、设计取舍、针对性测试、实际问题和演示命令。状态／所有权／审批／副作用协议改变后运行相关回归；阶段收尾按影响执行完整回归与开发验收。长时运行只在运行协议或未解决稳定性问题需要时重跑。任何被复现的核心正确性缺陷优先修复，再继续功能扩展。

本轮不设置统一“匹配率”或求职成功率。每阶段将具体 JD 要求映射到实现、演示与证据，依据投递反馈调整侧重点。
